# Feature list — PRD
Status: SHIPPED 2026-10-02 (PR #54) · Owner: George · Last updated: 2026-10-02

## Problem
No repo has one place that says what the product does, what is being built,
what is queued and what was retired. Today an agent that wants the answer
reads `docs/specs/README.md`, `docs/prd/README.md`, line 2 and the State
block of every open PRD (5k to 15k tokens), and still cannot see a removed
feature or an idea that has no PRD yet. hypertrophy-goals keeps a
hand-written master list (`docs/PRD.md`, `SHIPPED` / `PINNED` / `PLANNED`
markers) that drifted from its 30 per-feature PRDs within three weeks. The
owner wants every repo to have such a list, usable by agents to understand
state.

## Goals / Non-goals
- Goals: one file per repo listing every feature with a lifecycle state;
  generated from the files that already hold the truth, so it cannot drift;
  cheap to read (≤2k tokens); checked by prd-lint; a path for repos that
  already keep a hand-written list.
- Non-goals: generating the specs and PRD README indexes (a later step);
  release notes or a changelog; dates or ETAs for planned work; a Paused
  state (a stalled PRD is split instead).

## Research (what the best products do → adopt / adapt / reject)
Relies on: [feature-list](../../research/feature-list.md).
| Pattern | Seen in | Verdict | Why |
|---|---|---|---|
| Specs vs changes vs archive, generated `list` view, REMOVED delta retires a capability | OpenSpec | adopt | Same model the template already uses |
| Shared file built from per-change records | towncrier, changesets | adopt | No hand-merged list, no drift |
| Status inside each record plus a generated index | ADRs, adr-tools | adopt | Truth stays in the PRD and spec |
| State derived from evidence | Unleash, KEPs | adopt | Agents cannot forget to update it |
| Deprecated then Removed pair | Keep a Changelog, Backstage | adapt | As states, not a hand-kept log |
| Capped ordered queue, dropped ideas deleted | Shape Up | adapt | The `## Next` table (≤10 rows) |
| Hand-set roadmap statuses, Paused | Linear, Productboard | reject | Drift; scripts need a fixed vocabulary |
| Alpha / beta / GA stages | GitHub roadmap, Kubernetes | reject | Not how these repos ship |

## Users
Agents proposing a PRD (overlap check, Spec delta target), answering "what
exists" or resuming work; the owner scanning the product at a glance.

## Expected behavior

### 1. Generator and file
1. `features.sh` (in `claude-home/skills/implement-prd-section/scripts/`,
   next to `state.sh` and `prd-lint.sh`) writes `docs/FEATURES.md` from the
   repo it runs in. `--check` writes nothing and exits 1 with
   `docs/FEATURES.md: stale, run features.sh` when a fresh render differs;
   `--json` prints the rows as JSON. No `docs/specs/` and no `docs/prd/` →
   exit 2 with a message.
2. File shape: line 1 `# Features`, line 2
   `<!-- generated by features.sh from docs/specs, docs/prd, docs/prd/archive; do not edit -->`,
   line 4 a count line (`2 building · 1 pinned · 0 deprecated · 3 planned · 9 shipped · 1 removed`),
   then one table `| Feature | State | What it does | Spec | Change | Updated |`.
3. States, derived, never typed:
   - BUILDING: an open PRD (in `docs/prd/`, not README, not the
     migration plan) with Status `BUILDING` or any `[x]`/`[~]` Sections
     item. It marks every existing spec its delta names, and has its own
     row when it ADDs a spec that does not exist yet or names no
     existing spec.
   - PINNED: a spec exists and an open PRD that is not BUILDING has a
     delta naming it, or a `## Next` row targets it.
   - DEPRECATED: a spec exists and an open PRD's delta has a whole-file
     `REMOVED` entry for it.
   - PLANNED: the own row of an open PRD that is not BUILDING (it ADDs a
     spec that does not exist yet or names no existing spec), or a
     `## Next` row targeting `new`.
   - SHIPPED: a spec exists and nothing open targets it.
   - REMOVED: an archived `SHIPPED` PRD has a whole-file `REMOVED` entry
     for a spec that no longer exists; newest 10 shown.
   - Precedence per spec: DEPRECATED > BUILDING > PINNED > SHIPPED.
     `SUPERSEDED` and `DROPPED` PRDs are not listed. `repo-setup.md` is not
     a feature and is not listed.
4. Rows:
   - Feature: spec stem; for a PRD's own row, the PRD stem; for a Next
     row, its idea slug (lowercase kebab, ≤40 characters).
   - What it does: the specs index Capability cell, else the PRD H1 title
     without ` — PRD`, else the Next idea text; cut at 60 characters.
   - Spec: `[spec](specs/<x>.md)` or `-`.
   - Change: `[<prd stem>](prd/<prd>.md) <k>/<n>` (Sections done / total)
     or the Status word when there is no `Sections:` list; `Next #<n>`; the
     archive link for REMOVED; else `-`. Several open PRDs on one spec:
     the one that decided the state, then `+<m>`.
   - Updated: the PRD's `Last updated` date, else the last commit date of
     the spec, else `-`.
   - Order: BUILDING, PINNED, DEPRECATED, PLANNED (Next order, then PRDs by
     name), SHIPPED (by name), REMOVED (newest first). Same tree →
     byte-identical output.
5. Size: more than 60 rows → the file is still written, and `--check`
   adds `docs/FEATURES.md: over 60 rows; group specs or trim` (exit 1).
6. `docs/prd/README.md` gains, after `## Index`:
   `## Next (ideas without a PRD, in intended order; ≤10)` with table
   `| # | Idea | Targets | Notes |`. Targets is a spec stem or `new`.
   Writing the PRD deletes the row in the same commit; dropping an idea
   deletes it.
7. A `features` quiet-check target runs the generator's tests.

### 2. Lint
`prd-lint.sh` adds, when `docs/specs/` exists:
1. Spec delta grammar: every top-level bullet under `## Spec delta` starts
   with `ADDED`, `MODIFIED` or `REMOVED` followed by a backticked
   `docs/specs/<x>.md`, or is `none — <reason>`. Prose lines that are not
   bullets are allowed.
2. The specs index and `docs/specs/*.md` (minus README) match one to one:
   `<file>: spec not in docs/specs/README.md index` /
   `docs/specs/README.md: index row for missing <file>`.
3. Every `## Next` row's Targets is an existing spec stem or `new`; at
   most 10 rows.
4. When `docs/FEATURES.md` exists, `features.sh --check` must pass; its
   message becomes a violation.

### 3. Writers and readers
1. `/implement-prd-section`: the PRD lint paragraph runs `features.sh`
   before `prd-lint.sh` whenever `docs/FEATURES.md` exists, and stages it.
   Step 1 does not load it (builds stay scoped).
2. `/handoff` regenerates it the same way.
3. `migrate-prds` fold and split run `features.sh` before committing.
4. `adopt` and `bootstrap.sh`: the template ships `docs/FEATURES.md`;
   `adopt` generates it in the target (created, or unchanged when
   current) and the CLAUDE.md skeleton's repo map gains:
   `- \`docs/FEATURES.md\` — generated feature list and lifecycle state; read it before proposing a PRD or answering what exists.`
   `bootstrap.sh` regenerates it after emptying the indexes.
5. The PRD template's Propose step (`docs/prd/README.md` §Lifecycle 1)
   says: read `docs/FEATURES.md` first; delete the Next row the PRD
   replaces.

### 4. Master list migration
`migrate-prds` gains guidance for a hand-written master list (a file whose
`###` headings carry `SHIPPED`, `PINNED` or `PLANNED`, like hg
`docs/PRD.md`), applied during `fold`:
1. Product-level sections (vision, glossary, users, non-goals, key
   artifacts) fold into `docs/specs/product.md`.
2. Each SHIPPED or PINNED heading folds into its capability's spec (one
   group per capability, as in fold step 1).
3. A PINNED heading's queued follow-up and every PLANNED item become
   `## Next` rows in the old order; items past 10 go to the owner to drop
   or turn into PRDs. Long design notes move to `docs/research/`.
4. The file is archived as `SUPERSEDED by docs/FEATURES.md` with a
   mapping table (old heading → row or spec) in the archive commit body;
   done when every old heading maps to one row or to `product.md`.

## Data & contracts
- `docs/FEATURES.md` (generated), `## Next` table in `docs/prd/README.md`.
- `features.sh [--check|--json] [repo]`; JSON: list of
  `{feature, state, what, spec, change, updated}`.

## Acceptance criteria
- [ ] `features.sh` on this repo writes `docs/FEATURES.md` with every spec
      and open PRD as a row; a second run changes nothing; `--check`
      passes, and fails after editing a PRD Status line.
- [ ] Fixtures cover each of the six states, precedence, the 60-row
      warning, Next rows and the byte-identical rerun.
- [ ] prd-lint flags a bad delta bullet, an unindexed spec, a dead index
      row, a bad Next target and a stale `docs/FEATURES.md`, each with one
      violation; this repo lints with 0 violations.
- [ ] `adopt` on a fixture repo creates `docs/FEATURES.md` and the repo
      map line; `bootstrap.sh` leaves an empty-state file.
- [ ] hypertrophy-goals (rollout §4) ends with `docs/FEATURES.md` and
      `docs/PRD.md` archived as SUPERSEDED, every old heading mapped.
- [ ] Budget: `features.sh` < 1 s on a 100-PRD fixture; the file is ≤60
      rows and ≤2k tokens on this repo.

## Open questions
1. Where does `features.sh` live? Proposal: in the implement-prd-section
   skill's `scripts/`, like `state.sh` and `prd-lint.sh`, so every writer
   finds it and repos carry no copy that drifts.
2. Should a section marker alone make a PRD BUILDING, or should
   `/implement-prd-section` set Status `BUILDING`? Proposal: derive it
   from the markers; no Status edit and no new lint rule, so existing PRDs
   need no change.
3. Generate the specs and PRD indexes too? Proposal: later, in a separate
   PRD, once each spec and PRD carries its one-line summary.
